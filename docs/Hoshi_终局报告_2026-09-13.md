### 2.1 硬止损阈值（本次主实验）

| 组 | 窗数 | 几何 −6.0% | 几何 −8.2% | 差 | 胜/负 | t | p |
|---|---:|---:|---:|---:|---:|---:|---:|
| 第1组 | 30 | +93.65% | +76.03% | +17.62pp | 26/4 | 4.78 | 0.0001 |
| 第2组 | 30 | +75.69% | +62.26% | +13.43pp | 25/5 | 3.51 | 0.0003 |
| **合并** | **60** | **+84.45%** | **+69.00%** | **+15.45pp** | **51/9** | **5.77** | **<0.0001** |

尾部同步改善：最差窗 **−5.85% vs −8.75%**，负窗 **5/60 vs 7/60**。

**优势随持有期单调放大**（这是"该用 −6.0%"最硬的论据，证明它不是噪声）：

| 长度 | 12月 | 24月 | 36月 | 48月 | 60月 | 84月 | 96月 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 均差 pp | +5.32 | +4.68 | +11.09 | +8.99 | **+29.67** | **+66.67** | **+60.38** |
| 胜/负 | 11/3 | 11/3 | 6/0 | 4/3 | **6/0** | **7/0** | **6/0** |

机制：更早砍掉深跌头寸 → 资金更快周转到新的超跌信号 → 长周期靠复利放大。

### 2.2 外部 90 窗报告的独立复核

对另一 agent 的报告做**原始数据级复核（41 项全符）**：总账、回撤、换手、配对检验、
R3 触发数、持有期分档——**无一处算错**。

但发现它**最核心的论断无法用其提供的数据验证**：它给的 CSV 只有 `p6(−6.0·R3开)`
和 `B(−8.2·R3关)` 两个配置，而这两个**同时差了两个参数**，无法分离阈值效应；
其 2×2 消融里的 `A`、`C` 两个配置的逐窗数据未提供。

**解决方式**：本机用另一套引擎独立复现——效应量 +12.86pp vs +15.45pp 高度吻合。

### 2.3 同窗口跨引擎等价性

把外部那 90 个窗口原样喂进本机引擎跑同一配置（本金对齐 30 万）：

| 指标 | 值 |
|---|---:|
| Pearson r | **0.9779** |
| 均值差 | +6.01pp |
| 几何收益 | 本机 +55.19% vs 外部 +51.05%（差 4.14pp）|

→ 两套引擎测的是同一件事，所以对方的 A/C 对照口径可信，可与本机结论并列引用。
（本机数据多 200 个交易日、MA60 预热更充分，故系统性略高。）

### 2.4 R3 门控的真实影响（修正了此前的错误说法）

此前"关 R3 零影响"的说法**只对当下实盘账户成立**（`hoshi_live_trades` 至今 0 笔平仓 → R3 无输入）。
外部报告实测：p6 在 **90/90 窗口全部触发 R3，总停手 532 次，平均每窗 5.91 次**。

**一旦开始有平仓记录，R3 会高频介入**，且它是顺周期的错误风控
（用已完成交易的复利链算回撤，回撤系统性高估；触发后停手 60~120 天，
而超跌反弹策略在权益回撤后恰是信号最肥的时段 → 每次在最优点强制离场）。

## 三、最优方案 B′ 完整规格（可脱离代码独立实现）

> 以下规格精确到常量级。后续"重建验证"只依据本节，不参考任何现有代码。

### 3.1 数据与标的池

- 日线字段：`date, open, high, low, close, volume`，**不复权原始价格**。
- 标的池白名单（用白名单而非黑名单，因为库里混着指数、ETF、债券、国债逆回购）：
  `sh600/601/603/605/688/689` + `sz000/001/002/003/300/301`
- 剔除：名称含 `ST`/`*ST`、含 `退`、以 `N` 开头（上市首日）。
- 每个标的至少需要 **66 根 K 线**才参与计算。

### 3.2 每日扫描流程（按交易日顺序）

对每个交易日 `today`：

1. **先处理持仓出场**（见 3.5），回收资金。
2. **计算市场广度**（仅当"允许开仓"且持仓数 < 10 时）：
   - 对每个**至少有 66 根 K 线**的标的，取**截止昨天**的收盘序列 `cp`
   - 若 `len(cp) >= 60` 且 `MA60 = mean(cp[-60:]) > 0`：计入 `n_valid`；
     若 `cp[-1] > MA60` 则再计入 `n_above`
   - `breadth = n_above / n_valid * 100`（`n_valid >= 30` 才有效）
   - **广度门控：`breadth < 20.0` → 当日不开任何新仓**
3. **扫描信号**：对每个未持仓标的，取截止昨天的 OHLC 序列，计算评分（见 3.3）。
4. **买入**：信号按**评分降序**排序，依次尝试买入（见 3.4）。

### 3.3 入场信号与评分

设序列截止昨天，长度 `n`，索引约定：
`closes[-1] = D-1`（确认日）、`closes[-2] = D-2`（企稳日）、`closes[-3] = D-3`、`closes[-4] = D-4`。

**前置条件（任一不满足即无信号）**

1. `n >= 65`
2. `MA20 = mean(closes[-20:])`，`MA60 = mean(closes[-60:])`
3. `MA60 > 0` 且 **`MA20 > MA60`**（要求多头排列）
4. 定义日涨幅 `chg(i) = (closes[i] - closes[i-1]) / closes[i-1] * 100`
   - `chg_d3 = chg(n-4)`、`chg_d2 = chg(n-3)`、`chg_d1 = chg(n-2)`、`chg_d0 = chg(n-1)`
5. **连跌**：`chg_d3 < -2.0` **且** `chg_d2 < -2.0`（两天都必须满足）
6. `total_drop = chg_d3 + chg_d2`（负数）
7. **企稳日**（索引 `n-2`，其 OHLC 记为 `o1,h1,l1,c1`）满足以下之一：
   - 是锤子线，或
   - 是十字星，或
   - `-2 <= chg_d1 <= 5` 且 `c1 > 0` 且 `|c1 - o1| / c1 < 0.03`
8. **确认日收阳**：`chg_d0 > 0`

**K 线形态定义**（`rng = h - l`，`body = |c - o|`，
`lower = min(o,c) - l`，`upper = h - max(o,c)`）

- 锤子线：要求 `rng > 0 且 c > 0`，且
  `body/rng <= 0.3`，且
  （`body > 0` 时 `lower >= body*1.5`；`body == 0` 时 `lower >= rng*0.4`），
  且 `upper <= rng*0.5`
- 十字星：`rng > 0 且 c > 0` 且 `body/rng < 0.15`

**评分 `_calc_score`**（满分 10，四舍五入到 1 位小数）

```
score = 3.0
d = abs(total_drop)
if   10 <= d <= 25: score += 2.0
elif d > 25:        score += 1.5
elif d >= 5:        score += 1.0

if   锤子线(o1,h1,l1,c1): score += 2.5
elif 十字星(o1,h1,l1,c1): score += 2.0
else:                     score += 1.0

ls = min(o1,c1) - l1 ;  rng1 = h1 - l1
if rng1 > 0 and ls/rng1 > 0.5: score += 1.0

if   chg_d0 > 5: score += 1.5
elif chg_d0 > 2: score += 1.0

score = min(score, 10.0)
```

**信号合格**：`score >= MIN_SCORE`。

### 3.4 买入执行

- **买入价 = 当日 `open`**
- 最多同时持有 **10** 只；当日买入只数不限
- 单笔预算：`budget = equity * 0.10`，其中
  `equity = 当前现金 + 所有持仓的成本之和`（**用成本，不是市值**）
- `shares = floor(budget / buy_price / 100) * 100`（100 股整手）
- 买入费 `= max(成交额 * 0.00025, 5.0)`；总成本 `= 成交额 + 买入费`
- 若总成本 > 现金：改用 `floor(现金 / buy_price / 100) * 100` 重算；仍不足则跳过该信号
- 扣减现金，建仓。持仓 `hold_day` 初始为 0，买入当天推进为 **1**
- **T+1**：买入当天不允许卖出

### 3.5 出场规则（逐日推进，`hold_day` 简称 `hd`）

买入当天（`hd` 计为 1）就用当日 OHLC 推进一次状态，但不允许卖出（T+1）。

**出场模式**：`AUTO`——看最近 **10 笔已完成交易**的平均收益率，
若 `< -1.0%` 则用 `S4` 模式，否则 `S3` 模式。

**A. 止盈武装**

- `S3` 模式：
  - `hd == 14` 且未武装：若 `high >= entry * 1.052` → 武装，`trail = 1.2%`；否则 `peak = max(peak, high)`
  - `hd == 15` 且未武装：若 `high >= entry * 1.032` → 武装，`trail = 1.0%`
  - `hd > 15`：`peak = max(peak, high)`
- `S4` 模式：每天（未武装时）若 `high >= entry * 1.052` → 武装，`trail = 1.2%`；否则更新 `peak`

**B. 止盈卖出**（已武装）
`peak = max(peak, high)`；`trail_price = peak * (1 - trail/100)`；
若 `low <= trail_price` → **以 `trail_price` 卖出**。

**C. 提前硬止损兜底**（仅当 `LOSS_HARD_START_DAY < LOSS_START_DAY`，即 5 < 15 时生效）
若 `LOSS_HARD_START_DAY <= hd < 15` 且未武装：
若 `low <= entry * (1 + LOSS_HARD_PCT/100)` → **以该价卖出**。

**D. 反弹卖出式止损**（`hd >= 15` 且未武装）

- 若尚未 `loss_armed` 且 `low <= entry * (1 - 5.2/100)` → `loss_armed = True`，`trough = low`
- 若已 `loss_armed`：
  - `trough = min(trough, low)`
  - `rebound = trough * (1 + 2.2/100)`；若 `high >= rebound` → **以 `rebound` 卖出**
  - 若 `trough <= entry * (1 + LOSS_HARD_PCT/100)` → **以该价卖出**（硬止损）

**E. 超时**：`hd == 25` 且未武装 → **以当日 `open` 卖出**

**F. 兜底**：`hd >= 40` → **以当日 `close` 卖出**

**卖出费** `= max(成交额*0.00025, 5.0) + 成交额*0.0005（印花税）`
`+ 成交额*0.00001（过户费，仅代码以 `6` 开头的沪市）`

**期末处理**：窗口结束时仍未平仓的持仓，按**窗口内最后一个交易日的收盘价**平掉
（不使用数据集最后一根 bar——这是 exp5 修复过的关键 bug）。

### 3.6 R3 门控（原版启用，**B′ 关闭**）

- 用**已完成交易的复利链**计算权益与回撤（不含现金与未平仓持仓）
- 回撤 `< -25%` → 触发停手
- 冷却：首次 **60 自然日**；恢复后 **120 自然日内**再次触发则升级到 **120 自然日**（封顶）
- 停手期间不开新仓

## 六、方法论事故（必须记录）

1. **锚点跨版本失效**：8 个锚点中 3 个对不上（`end ≤ 2016` 全对、`end ≥ 2024` 全错，差 −2~−3pp）。
   - 已排除：强平 bug（期末未平仓 = 0）、末端新增 bar（代码层面被过滤）
   - **更正**：回测内部广度是**引擎自计算**的（基于 CSV 数据），
     并不依赖 `hoshi_market_features.csv`——因此"广度表漂移"这一解释**存疑**，
     更可能是**引擎代码在锚点之后被修改**（`hoshi_backtest_exp5.py` 时间戳晚于锚点）。
     归因尚未 100% 定论。
   - **影响可控**：`t6` 与 `t8` 用同一套代码与数据，差分完全有效 → 主结论不受影响。
2. **回测输入未纳入版本控制**：`hoshi_market_features.csv`、`hoshi_csv_long/` 均未被 git 跟踪。
   已新增 `scripts/freeze_data_version.py` 产出 `hoshi_data_version.json` 指纹。
3. **并行度必须实测**：exp5 加载全量 K 线约 **6GB/worker**（不是估的 2.5GB），
   32GB 机器上并行度上限 ≈ 4–5，否则 OOM。
4. **目录 `.git` 归属**：接手已有目录做 git 操作前，必须先看 `git remote -v`
   和 `git log` 的作者分布。
