## 一、为什么做这次对照

实盘 live engine 用 `LOSS_HARD_PCT = -6.0%`，而此前 60 窗验证方案 B 时用的是**引擎默认 −8.2%**。

两者**从未联合验证过** —— 此前 60 窗只验证了「硬止损**启用日** = 5」（`LOSS_HARD_START_DAY`），
**不是阈值本身**。另一个 agent 用 90 窗独立报告提出「−6.0% 优于 −8.2%，不该放宽止损」，
但其 A/C 配置的逐窗数据未公开，无法核对。故本机用另一套引擎独立复现。

## 七、⚠️ 必须记录的方法论事故：锚点跨版本失效

本次跑批的 t8 锚点复核有 **3 处对不上**（另 5 处逐位吻合）：

| 窗口 | 本次 t8 | 9-11 锚点 | 差 |
|---|---:|---:|---:|
| 2022-02~2025-01 | +25.8576% | +27.9341% | −2.08pp |
| 2017-09~2024-08 | +93.4770% | +96.0018% | −2.52pp |
| 2017-10~2024-09 | +94.9420% | +97.9054% | −2.96pp |

**规律：end ≤ 2016 的窗口全部吻合，end ≥ 2024 的全部不吻合。**

已排除的假设：
- ❌ **H1 数据末端新增 9-07~9-11 的 bar** —— `run_backtest` 在 `dates` 层就过滤了 end 之后
  全部日期（`exps5.py:594-600`），且 `bar_on` 用 `idx_of[code].get(today)` 精确匹配，
  末端新增数据在代码路径上无法影响。
- ❌ **H3 exp5 期末强平残留 bug** —— A 组实测「**期末未平仓 = 0**」，根本没走强平路径。

**唯一剩余候选 H2：广度门控数据漂移。**
`hoshi_market_features.py:28-30` **直接从 `data/tdx.duckdb` 实时计算广度**：

```python
con = duckdb.connect('data/tdx.duckdb', read_only=True)
... FROM raw_kline_daily k LEFT JOIN raw_symbol_name n USING (symbol)
    WHERE {白名单} AND (n.name IS NULL OR (n.name NOT LIKE '%ST%' AND n.name NOT LIKE '%退%'))
```

而 9-11~9-12 做过 **TDX 全量增量刷新（7413/7698 只）**，
且该特征表时间戳 **9-12 00:47 晚于锚点 9-11 10:13**。
只要刷新改动了历史 K 线或名称表里的 ST 标记，**历史广度值就会整体漂移** → 门控结果改变 → 回测数值变化。
（近期数据被修正得更多，故只有 end ≥ 2024 的窗口受影响。）

**诊断实证结果**（`_diag_anchor.py`，窗口 2022-02-01~2025-01-31）：

| 配置 | 收益 | 买入笔数 | 期末未平仓 |
|---|---:|---:|---:|
| A 原样（BREADTH=20） | +25.8576% | 382 | 0 |
| B 关闭广度门控 | **+39.8546%** | 448 | 0 |
| C 门控阈值=0（永久放行） | +39.8546% | 448 | 0 |
| D 门控阈值=100（永久拦截） | **+0.0000%** | **0** | 0 |
| E 原版（8分/止损15/无门控） | −6.9601% | 525 | 0 |

- **广度门控对结果的影响幅度 = +13.997pp**（开 vs 关）——
  门控握着 ±14pp 的杠杆，广度值只需漂移很小的量，就足以解释观测到的 −2~3pp 差异。
- **D 组全拦截得到精确 0.0000% 且 0 笔买入** —— 反证引擎与门控逻辑本身正确，差异不是 bug。
- A 组结果可稳定复现（两次跑均 +25.8576%）。

→ **H2 成立**：锚点差异来自 `hoshi_market_features.csv` 在锚点（9-11 10:13）之后
被重算（9-12 00:47），历史广度值随 duckdb 刷新而漂移。

⚠️ **对既有结论的量化外推**：本轮 3 个错配锚点的偏差为 **−2.1 ~ −3.0pp**。
按此量级外推，9-11 之前那些结论的绝对数值在当前数据下会有同量级偏移
（例如方案 B 的 60 窗几何 +69.13% 大致落在 +66~67%），
**方向与相对排序不变，但跨版本引用时必须按漂移量折减**，或干脆用当前冻结版本重跑。

**影响评估（关键）：**
- ✅ 本次 `t6` 与 `t8` **用同一套 market_features**，两个分支受完全相同的数据漂移影响，
  差分因此完全有效 → **第三节的主结论不受影响**
- ⚠️ 但**跨版本的绝对数值不可直接比较**：9-11 及之前的全部结论（方案 B 的 60 窗 +68.17pp、
  T5 消融等）基于旧广度表，与本轮数值不能混用

## 八、随之暴露的两个工程问题

1. **关键回测输入未被版本控制**
   `git ls-files` 显示 `hoshi_market_features.csv` 与 `hoshi_csv_long/` **均未被 git 跟踪**（`?? 未跟踪`）。
   → 数据无历史版本，漂移无法回溯、结论无法复现。
2. **广度表是"活"的**
   它每次都由 duckdb 实时计算，而 duckdb 被增量刷新 → 同一份代码在不同日子跑出不同结果。
   → 必须**冻结**：每次刷新后重算，随即记录指纹，并与上一版 diff。

**已采取的措施**：新增 `scripts/freeze_data_version.py`，产出 `hoshi_data_version.json`：
```
market_features  sha256 2075030173721a830f06a69b20647ff81af5980a545cf810eda678a33be7c4e2
                 rows 4203   range 2009-06-01 ~ 2026-09-11   size 405429
hoshi_csv_long   files 5262  total_bytes 555179440  manifest_sha256 4291277c…b531
anchor_files     abl1_b a6949525d84dc5f9   abl2_b b39830dafef2fc5f
```
今后每次刷新数据后重跑该脚本并 diff，即可第一时间发现漂移。
