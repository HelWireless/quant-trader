# Hoshi-cplus 实盘邮件 vs 本地扫描 —— 差异排查（2026-09-14）

## 0. 现象

| | 本地（我跑的） | 服务器实盘邮件 |
|---|---|---|
| 数据截至 | 2026-09-11（周五） | 2026-09-14（周一） |
| 扫描目标 | 9-14 买入 | 9-15 买入 |
| 广度 | 53.6%（9-11） | **50.8%（9-14）** |
| 买入候选 | **0**（当日仅 3 信号，评分 5/6/6，全 <9） | **3**：002365(10.0)、300901(9.5)、300736(9.0) |

→ 乍看"结果不一样"，实际是**三处口径差异叠加**，不是策略或数据出错。

---

## 1. 差异一：数据 / 信号日不同（最主要）

- 本地数据当时停在 **9-11**；服务器已刷新到 **9-14**。两边扫描的**确认日**不同：
  - 本地：确认日 = 9-11 → 信号用于 9-14 执行 → 0 个合格。
  - 服务器：确认日 = 9-14 → 信号用于 9-15 执行 → 3 个合格。
- 两个都对，只是**不在同一天**。9-11 与 9-14 的信号列表本来就不一样。

## 2. 差异二：包 `--scan DATE` 的"确认日"语义（关键，易踩）

- `hoshi_cplus/data.py:precompute` 里，`sig_by_date[d]` 是用 **`bars[:k]`（截止 d 的前一根）**
  算出来的 → 即 **`sig_by_date[d]` 的确认日 = d 的前一交易日**。
- 因此 `--scan 2026-09-14` 实际用的是 **9-11 的数据**（确认日 9-11），
  并不是"用 9-14 收盘算、9-15 买"。
- 服务器脚本（`scripts/hoshi_premarket_guide.py`）用的是 **live 模式**：
  **确认日 = 最新一根 bar（9-14）**，执行日 = 下一交易日（9-15）。
- 包还有一处口径差：`orders.py:build_plan` 把 `exec_day` 写成 `signal_day + 1`，
  而回测是"以 signal_day 为执行日"——**包的 scan/build_plan 对"最新收盘→次日买"这条路径
  存在一天错位**，必须用 live 模式才能对齐实盘。

**→ 本地要复现服务器，必须按 live 模式算信号（确认日 = 最新 bar），而不是 `--scan 最新日`。**

## 3. 差异三：涨停过滤（本地多算了 1 只）

- 用 live 模式复现，本地得到 **4 只**：002365(10.0)、**605168 三人行(10.0)**、300901(9.5)、300736(9.0)。
- 服务器只列 3 只，**少了 605168**。原因：
  - 605168 在 **9-14 涨停**：O45.00 H50.11 C50.11，涨幅 **+10.01%**，**收=最高（封板）**。
  - 涨停板开盘**买不进**（封单），实盘指导必须剔除 → 服务器有此过滤，**包的 scan 没有**。
- 结论：3 vs 4 的差异 = 服务器正确地过滤了涨停票。

## 4. 差异四：广度口径不同

- 本地：包口径（9-11 收 > MA60）= **43.9%**；live 口径（9-14 收 > MA60）= **45.6%**。
- 服务器：**50.8%**。三者都 > 20% 门控，**不影响"是否开新仓"的决策**，但口径不同值得统一。

## 8. 建议（改进项）

1. **给 `hoshi_cplus` 的 scan 加 live 模式**：`--live`（确认日 = 最后一根 bar，执行 = 下一交易日），
   避免"最新收盘→次日买"被 `--scan 最新日` 的一天错位坑到。
2. **scan 增加涨停过滤**：确认日涨幅 ≥9.8% 且收≈最高 → 剔除（开盘买不进）。
3. **统一广度口径**：与服务器对齐（若采用 50.8% 的算法），否则邮件/本地数字不一致易误判。
4. 把「live 模式 + 涨停过滤 + 广度口径」固化进 `hoshi_premarket_guide.py`，与此文档同源。
