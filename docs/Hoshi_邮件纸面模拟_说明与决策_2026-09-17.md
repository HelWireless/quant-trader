# Hoshi-cplus 邮件纸面模拟 —— 说明与决策记录

> 日期：2026-09-17　｜　面向：其他 agent / 协作者
> 一句话：我搭了一个 **30 万本金、纯纸面**的 hoshi-cplus 模拟，信号来自每日 QQ 邮件「Hoshi实盘」。
> **本文重点解释：为什么「服务器邮件里的买入清单」和「我用同一套策略本地复算的结果」不一样。**

---

## 0. 先给结论（TL;DR）

1. **两边用的是同一套策略（hoshi-cplus），不是两个策略。**
2. 不一致的原因是**「服务器那份邮件」当天扫描不全**：
   - 2026-09-17 的邮件只列了 **3 只**买入，我用同一套 hoshi-cplus 代码本地复算出 **5 只**，
     且经逐只复核，**5 只全部合规**——邮件**漏了 2 只**（000011 深物业A、600108 亚盛集团），
     同时把**确认日涨停**（开盘大概率买不进）的 600822 上海物贸列了进去。
3. 因此本项目采用：**双源交叉核对，不一致时以「本地复算」为准，并剔除确认日涨停的票。**

---

## 1. 两套信号源

| | 来源 A：服务器邮件 | 来源 B：本地复算 |
|---|---|---|
| 生成者 | `scripts/hoshi_premarket_guide.py`（跑在服务器 `cody_pc`） | `scripts/hoshi_scan_live.py`（用 `hoshi_cplus` 包） |
| 送达方式 | **自发邮件**到 QQ 邮箱（发件人＝收件人＝`2587225803@qq.com`，主题 `Hoshi实盘 YYYY-MM-DD`） | 本地 CSV/duckdb 直接计算 |
| 读取方式 | qq-mail 连接器 `SearchMessages(dir="sent", q="Hoshi实盘")` + `GetMessage` | 终端运行脚本 |
| 落地 | 邮件正文（第一节「⚡ 明日要动手的事」） | stdout / JSON |

理想情况下 **A == B**（同策略、同数据、同参数）。**实际不相等。**

## 2. 实证：2026-09-17（确认日）→ 2026-09-18 买入

| 来源 | 买入清单 |
|---|---|
| **邮件 A** | 300970 华绿生物(9.5)、300061 旗天科技(9.0)、**600822 上海物贸(9.0)** |
| **本地 B** | 300970(9.5)、**000011 深物业A(9.0)**、300061(9.0)、**600108 亚盛集团(9.0)**、600822(9.0) |

### 逐只复核（用 `hoshi_cplus.signals.detect_signal` + 均线，数据刷到 9-17）

| 代码 | 名称 | 9-17 涨幅 | MA20 | MA60 | MA20>MA60 | detect_signal | 邮件是否列出 |
|---|---|---:|---:|---:|:--:|---:|:--:|
| 300970 | 华绿生物 | +4.32% | 19.192 | 18.071 | ✓ | 9.5 | ✓ |
| 000011 | 深物业A | +6.44% | 8.697 | 7.791 | ✓ | 9.0 | **✗ 漏** |
| 300061 | 旗天科技 | +7.91% | 6.500 | 6.468 | ✓ | 9.0 | ✓ |
| 600108 | 亚盛集团 | +6.82% | 4.133 | 3.419 | ✓ | 9.0 | **✗ 漏** |
| 600822 | 上海物贸 | +9.96% | 8.688 | 8.300 | ✓ | 9.0 | ✓（但**确认日涨停**，收=最高） |

**结论**：5 只全部满足 hoshi-cplus 入场条件（连跌两日 + 企稳 + 确认收阳 + MA20>MA60）。
邮件的 3 只只是子集，且包含了可买性最差的那只（涨停）。

## 3. 为什么会不一致（可能原因，按可能性排序）

1. **服务器当日数据有缺口 / 未补齐** —— 历史邮件里多次出现
   `⚠️ 数据不全`「股票池覆盖率 0/0 = 0.0%」等告警，缺数据的股票当天自然算不出信号 → 漏。
2. **涨停口径不稳定** ——
   - 09-14：服务器**剔除**了确认日涨停的 605168 三人行；
   - 09-17：服务器**保留**了确认日涨停的 600822 上海物贸。
   同一套逻辑两次表现相反，说明其过滤/数据状态不一致。
3. **两家实现细节可能不同** —— MA 窗口、复权处理、universe 白名单、最少 K 线根数、
   广度样本口径等，任一不同都会让边界个股的结论翻转。

## 4. 本项目采用的处理规则（供对齐）

- **双源交叉核对**：邮件 + 本地 `hoshi_scan_live.py` 都跑。
- **不一致时以本地扫描为准**（完整、可复核、同一份代码）。
- **剔除「确认日涨停」的票**：涨幅 ≈ +10%（主板）/ +20%（创业板·科创板）**且** 收盘≈最高（封板）。
  原因：涨停板次日大概率跳空高开甚至继续封板，**开盘买不进**。
- 汇报里**必须列出两源差异**。

> ⚠️ 另外一个纯工程坑（不同 agent 容易踩）：
> 本环境下有两个"mail"连接器——**qq-mail**（`mcp__qq-mail__*`）与 **agent-mail**（`mcp__agent-mail__*`）。
> 必须用 **qq-mail** 读 Hoshi 邮件；用成 agent-mail 会返回 `not_bound`，从而"读不到邮件"。
> 本项目自动化曾连续 4 天误用 agent-mail，导致一直没读到邮件、只能用本地扫描兜底。

## 5. 给其他 agent 的复现 / 对齐清单

1. **策略代码**：用本仓库 `hoshi_cplus/`（`preset='cplus'`：
   评分 ≥9 / 硬止损启用日 5 / −6.0% / **R3 关闭** / 广度门控 20%）。
2. **日期口径**：**确认日 = 数据里最后一根 bar**；**执行日 = 下一个交易日开盘**。
3. **入场条件**：连跌两日（单日跌幅 < −2%）+ 企稳日（锤子/十字/小实体）+ 确认日收阳，
   且 **MA20 > MA60**（趋势过滤）。
4. **过滤**：涨停 / 停牌 / 一字板要处理；无 66 根 K 线的剔除。
5. **数据**：先增量刷新并**清 9998 脏行**，再用两个 CSV 目录同步
   （`scripts/hoshi_csv_2005` 全市场用于广度、`scripts/hoshi_csv_long` 回测集）。
6. **别用前复权视图**（`v_stock_qfq` 历史上有损坏记录），用 raw / bfq。

```bash
# 最小复现（Linux/Mac/Windows 均可，需先备好数据）
python scripts/refresh_tdx_duckdb.py                              # 刷新行情到最新交易日
# 清脏行（duckdb）：DELETE FROM raw_kline_daily WHERE date > DATE '<今天>';  raw_basic_daily 同
python scripts/append_new_bars.py --dir scripts/hoshi_csv_2005
python scripts/append_new_bars.py --dir scripts/hoshi_csv_long
python scripts/hoshi_scan_live.py                                 # 打印确认日全部合格信号
```

## 6. 我为什么这么做（设计决策）

- **为什么不直接用邮件？** 邮件是服务器单一实现；实测会漏信号、且涨停口径不稳。
  做模拟要可复现、可核对，所以以**本地同一套代码**为准，邮件仅作对照。
- **为什么用 `hoshi_cplus` 这个包？** 它是经 180 窗双盲验证的唯一可信实现
  （见 `docs/Hoshi_终局报告_2026-09-13.md`），纯标准库、零依赖，任何人克隆即可复算。
- **为什么模拟要"纸面"？** 先把**信号与执行口径**跑通、把差异暴露出来，再谈实盘；
  符合"先 mock 跑通端到端、再上生产"的纪律。
- **为什么每天落台账（`ledger.csv`/`trades.csv`）？** 便于逐日对账、复算最大回撤与胜率，
  一个月后能给出"是否盈利"的定量结论。
- **为什么剔除涨停？** 涨停封板买不进，若把这类票当"已买入"计入，会高估收益（幸存者偏差）。
